7 Data & code sharing

TADA is about your code. This chapter covers everything sitting around it: what data to share, in what format, with what metadata, under what licence, and what a journal will check.

On this page: what archiving is for · vocabulary · what data to share · file formats · metadata · licences · the SORTEE guidelines · advice for authors · checklist

7.1 What archiving is for

This is worth stating explicitly, because the three goals pull in slightly different directions and different practices serve each one. The SORTEE guidelines set out three:

1 Data reuse Prevents data loss; enables research synthesis and meta-analysis; allows re-analysis as methods improve; and allows new questions to be asked of existing data, which in turn reduces the number of animals used in experiments.

2 Transparency Readers can see what was actually done to obtain the reported results. Open data will not stop fabrication, but it makes fabrication far easier to detect.

3 Computational reproducibility Someone else can reproduce the published results from the archived data and code.

Two further points from the guidelines are easy to miss:

  • Data are typically collected with public money, and so can be seen as a public good that should not be lost when a researcher changes job or a computer breaks. Lost data and code represent a substantial source of research waste.
  • Published results are often not described in enough detail to be included in a meta-analysis. Archiving the data lets a synthesist re-analyse them to get what they need, and substantially increases the evidence available for synthesis.

7.2 Vocabulary

Key terms from the SORTEE glossary (Table 1), because these terms are used loosely and the distinctions matter when someone asks you for “the raw data”.

Term Meaning
Metadata A description of, and information about, the data and code. Typically a text file called a README; variants include a codebook or a data dictionary.
Raw data Unprocessed and unfiltered data, including any raw files such as photos, audio recordings, videos and data sheets.
Data filtering Removing some data to create the dataset used in the analysis, for example removing individuals with a certain characteristic. The result is filtered data.
Data processing Transforming data from one form to another: extraction from images or video, summarising, transforming, calculating. The result is processed data.
Repository A framework providing long-term storage for many projects, such as Zenodo, Dryad or Figshare.
Project A collection of files archived for a specific manuscript. This is similar to what GitHub calls a repository, which is the source of some confusion.
Data editor An editorial position at a journal, responsible for screening and quality-controlling the data and code archived alongside manuscripts under review.
Data and code quality control Checking the suitability of data and code for public archiving.

Transcribing data from a written to a digital format, and the error-checking that follows, does not count as processing. A typed-up field sheet is still raw data.

7.3 What data to share

Ideally, both raw and processed data. The SORTEE guidelines state that ideally both raw and processed data are provided, and allow three acceptable forms, with (b) and (c) as fallbacks where a full raw upload is not possible:

a) Raw data, along with the processed data and/or the code to prepare the data for analysis.

b) A sample of raw data alongside the processed and filtered data, when a full raw data upload is not possible.

c) Processed and filtered data with a detailed description of how to both obtain and process or filter the raw data.

Raw data matter because without them nobody can check the filtering and processing steps, which is where undetected errors most often originate. Option (c) is acceptable, but it places the whole burden on your written description being complete.

7.4 File formats

The rule is the same for data as for code: universally interoperable, meaning the file can be exchanged and used across different software and operating systems.

Data formats

Prefer simple text-based formats. .csv, .tsv and .txt can be used by more software, across more systems, than anything else.

Format Verdict
.csv, .tsv, .txt Preferred. Maximally interoperable.
.parquet Interoperable, highly compressed, efficiently read, and highly accurate for large datasets.
.xlsx Not proprietary, so interoperable, but can carry information such as formatting that is lost on import into statistical software.
.xls Proprietary format. Avoid.
.RData, .rds Usable with open-source software, but requires knowledge of R to extract, and may depend on the R version used to save it. Restricts reuse.
.sps and other proprietary formats Not interoperable; do not facilitate reuse.
.pdf, .docx Never. Prone to error when copy-pasted, and cannot be readily imported into statistical programs.

SPSS .sps files appear here as unsuitable, yet Transferable gives them as an example of a file type that passes. Both are correct, because they are judging different things: this table concerns data files, where .sps is a proprietary format, whereas the Transferable test concerns code files, where an .sps syntax file can at least be opened in a text editor.

Where there is genuinely no alternative, as with data collected by proprietary software, provide the non-interoperable file alongside interoperable extracted data, with a clear description of the conversion process in the metadata, including the software version used.

Code formats

Code must be in a format that can be readily opened by text editors and IDEs such as VS Code: .R, .py, .cpp, and so on. See Transferable.

Code must not be provided as a .pdf or pasted into a Word document. Even where the script can be copied and pasted out, these programs often insert additional characters or spacing that the analysis software misinterprets. The canonical example is Python code that fails to run because the indentation was mangled.

7.5 Metadata: what a README must contain

The Documented chapter covers the code README in detail. The SORTEE guidelines set out what is needed on the data side, and the two overlap heavily.

General information

  • Manuscript title and abstract
  • Authors and relevant contact information
  • Date and location of data collection
  • A list of all relevant funders
  • Licence information, for example CC-BY
  • Information about data derived from other sources, such as other articles or online data

Detailed file descriptions

  • What each data file contains and how it is structured
  • What variables it contains
  • What units of measurement they are in
  • How they link to the data described in the manuscript, so that every column in a .csv is explained and described

Deliver this as part of the main README, as separate README files describing the data and code, or as a data dictionary per data file, for example a .csv with one column for variable names and another for their descriptions.

The bar the guidelines set for both data and code metadata is the word “adequate”: metadata detailed enough that anyone can understand the data, or the analysis code, without needing to read the manuscript. A README that only makes sense alongside your methods section does not meet that bar.

Under double-blind review, some sections can be left blank until acceptance and filled in then.

On LLMs. The SORTEE guidelines add that the README should state whether and how the authors have used large language models in code generation (Resnik & Hosseini 2025), while noting that a data editor is unlikely to be able to verify this.

7.6 Licences

Without a licence, data and code cannot be legally reused in many circumstances, depending on jurisdiction. Most researchers have little knowledge of licences, so this is a common and consequential gap.

For data

Typically Creative Commons licences. Chooser: https://creativecommons.org/chooser/

Licence What it means Notes
CC0 Public domain; no attribution required The most permissive. Default at Figshare; mandated by Dryad.
CC BY 4.0 Reusers must credit the original author, but may distribute, remix, adapt and build upon the material, including commercially Default at Zenodo.
CC BY-NC 4.0 As CC BY, but prohibits commercial use More restrictive.

For code

Software licences rather than Creative Commons. Chooser: https://choosealicense.com/

Licence What it means
MIT Very permissive: copy, modify, merge, publish and share, with the licence notice retained
BSD 2-Clause / 3-Clause Permissive, similar in spirit to MIT
Apache 2.0 Permissive, with an explicit patent grant
GPL v3.0 Copyleft: derivatives must carry the same licence, and changes from the source must be listed

The SORTEE guidelines suggest permissive code licences wherever possible, naming MIT, BSD 2-Clause, GNU and Apache (Stage 3.2).

CC0 is not well suited to code, which is why Dryad, being CC0-only, points code deposits at Zenodo.

Choosing

The SORTEE guidelines treat data and code differently. For data they do not recommend or enforce any specific type of licence, so the requirement is simply that you choose one and state it. For code they suggest permissive licences wherever possible, naming MIT, BSD 2-Clause, GNU and Apache (Stage 3.2).

Four further things should influence the choice:

  • Who the audience is, and whether commercial application is expected
  • Whether you want others to be able to modify or extend the work
  • What your journal, institution and funder require, since some journals mandate a licence on archiving; the Journal of Statistical Software requires a GPL
  • Whether your repository already applies one by default, or mandates one

In practice: pick a licence at https://choosealicense.com/, copy the licence text into a LICENSE file in the project, and name it in the README. Or select it in the repository’s deposit form, as Zenodo allows.

7.7 The SORTEE guidelines

The SORTEE guidelines for data and code quality control (Pick et al. 2026, Peer Community Journal 6: e20) are written for data editors, the editorial role responsible for screening and quality-controlling data and code at a journal. They are worth reading as an author precisely because they tell you what will be checked.

The limits of quality control. It is about ensuring archived data and code meet minimum standards: complete, usable, documented and runnable. It is explicitly not a code review. A data editor does not critique your analytical techniques, and it is not their role to review, interpret or correct your code, nor to check its reliability (Ivimey-Cook et al. 2023; Hillemann et al. 2025). That is what code review is for.

7.7.1 The six stages

Table 2 of the paper is reproduced in full below.

Stage Guideline
1. Data must be archived and adhere to FAIR guiding principles
1.1 Data files are accessible and in an open repository Data are open and freely available and are located in a permanent public repository with an associated globally unique persistent identifier, that is cited in the text and reference list of the manuscript.
1.2 Data are associated with a license Data must be associated with a license.
1.3 Data files are present and complete Authors must either provide: a) raw data, along with the processed data and/or code to prepare the data for analysis, or b) a sample of raw data alongside processed/filtered data when full raw data upload is not possible, or c) processed/filtered data with a detailed description of how to both obtain and process/filter the raw data.
1.4 Data files are in an interoperable format Data files must be provided in an interoperable format.
1.5 Data metadata is present and adequate Detailed metadata, including (but not limited to) a README file, must accompany the data.
2. Archived data corresponds with the data reported in the manuscript The structure and contents of the archived data files must match the description in the manuscript.
3. Code must be archived and adhere to FAIR guiding principles
3.1 Code files are accessible and in an open repository Code files are open and freely available and are located in a permanent public repository with an associated globally unique persistent identifier, preferably in the same archived project as the data files, and are cited in the text and the reference list of the manuscript.
3.2 Code is associated with a license The code must be associated with a license.
3.3 Code files are present and complete All code used for generating the results of the manuscript (including filtering, processing, graphing, and analysis) must be present either in one or more code files.
3.4 Code is in an interoperable format Code files must be provided in an interoperable format.
3.5 Code metadata is present and adequate A sufficiently detailed README must accompany the code. Code must also be broken into sections with clear annotation stating the purpose of the code with clear links to the relevant sections, figures, and tables in the manuscript.
4. Archived code corresponds with the workflow reported in the manuscript The structure and content of the archived code must match the description of data filtering, processing, and analysis, and the presentation of results in the manuscript.
5. Archived code runs with the archived data Code must be able to run without error using the archived data. With the exception of easy to fix file path errors, all errors should be addressed by the author.
6. Results can be computationally reproduced by running the archived code Results reproduced by the data editor with the archived data and code must match those presented in the manuscript. A tolerance threshold can be given when there is not an exact match but the authors must state clearly in the code metadata why this mismatch might occur. If saved model outputs are instead provided, this must also be clearly stated in the metadata.

7.7.2 How TADA maps onto the stages

Wiki guidance. TADA covers the author-side work for Stages 1 and 3 almost exactly:

TADA SORTEE stages
Transferable 1.4 and 3.4 (interoperable formats) and, in practice, 5 (code runs, since local file paths are the most common cause of failure)
Available 1.1 and 3.1 (open repository, PID, cited in the manuscript)
Documented 1.2, 1.5, 3.2 and 3.5 (licence and metadata)
Annotated 3.5 (sectioned code with clear annotation and signposting), and it is what makes Stage 4 assessable at all
(Not TADA: your responsibility as author) 1.3 and 3.3 (completeness), 2 (data matches manuscript), 6 (results reproduce)

7.7.3 Common failures at each stage

Drawn from the guidelines’ own account of common problems.

Stage 5, code runs. The most frequent causes of failure are:

  • a package or module not installed or loaded within the code
  • a missing code chunk
  • variable names in the code not matching those in the data files
  • code referencing data files whose names do not match the archived files
  • local or absolute file paths, singled out as one of the most common reasons that code does not run

Data editors are told to be pragmatic about paths. An absolute path, or a way of specifying relative paths they are not familiar with, should not be a reason to return the code, provided they can make it run with minor changes. It is logged as a minor error. Every other error is the author’s to correct, and it is explicitly not the data editor’s job to make your code run.

Stage 6, results reproduce. In most cases exact reproducibility is expected: the exact number in the manuscript should come out of the code. State any of the following legitimate reasons for a mismatch in the metadata:

  • Stochastic methods such as simulations and MCMC. Set a seed (set.seed() in R, random.seed() in Python) at the beginning of any code section that would be run independently, including for figure generation with jittering. Note that setting a seed does not always guarantee reproducibility.
  • Post-processing of figures in other software. The data in the figure are still expected to be the same, but the code may not reproduce the figure exactly.
  • Software version differences. If results are sensitive to the version used, flag it clearly and justify the version in the manuscript and metadata.

Computationally expensive or proprietary analyses. Where code needs specialist hardware, takes a very long time, or depends on proprietary software such as ASReml, full computational reproducibility cannot be assessed. In those cases:

  • Indicate it clearly in the metadata, alongside a saved output, for example large Bayesian model objects saved as .rds
  • Ideally provide example code demonstrating that the code will run, such as an analysis on a subset of the data, or a model run for a reduced duration
  • Where only part of the analysis needs proprietary software, say which parts a data editor can assess
  • Consider non-proprietary execution routes, such as GNU Octave for MATLAB code or MATLAB Compiler for standalone applications, but test compatibility and note any limitations in the metadata
  • Build systems such as targets (R) or Snakemake can provide reproducibility signatures (hashes) for computationally intensive steps, along with intermediate data objects

7.8 Advice for authors

The guidelines’ own suggestions, which are the highest-return habits here.

1. Adhere to the guidelines from the beginning of the study. Making a project accessible and reproducible at the end is a great deal of work. Create a clear directory structure and a README at the start, and update the metadata as new files are added. Annotate code as you produce it. Working with reproducibility in mind also makes it far more likely that someone else can reuse the project and successfully run the code, which matters a great deal if several people will touch the study over its lifetime.

2. Prepare data and code before submission to any journal. Having it ready minimises problems during submission and quality control, and makes transfer to another journal straightforward if the paper is rejected.

3. Perform a pre-submission code review. Send the project to a colleague or co-author before submitting. They can check that the code runs with the data in the structure provided, that the metadata is adequate, that data and code match the manuscript, and that results reproduce. Co-authors are also more likely to spot mistakes in the code, because they know the study and the data, and data editors do not check code reliability. See Code review.

4. Consider Markdown or Quarto. Presenting everything in one self-contained document is very helpful for data editors and future readers (Buckley et al. 2025), because it makes the link between code, data and outputs explicit.

Say what was checked. If your journal performs quality control, the guidelines suggest stating this in the data and code availability section, for example: “Data and code were checked from Stage 1–4 of the SORTEE guidelines for Data and Code Quality Control”. Note explicitly where a check could not be performed, whether because of proprietary software, sensitive data or computationally expensive analyses.
