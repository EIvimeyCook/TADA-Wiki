2 TADA at a glance

Transferable, Available, Documented, Annotated. Four steps that take analytical code from a working copy on one machine to an archived record that another researcher can still run.

2.1 Why another set of guidelines?

There is no shortage of advice on writing good code, but very little of it deals with the specific task of archiving an analysis.

The TADA authors identify three gaps in the existing resources:

  1. They do not sufficiently address how to archive analytical code.
  2. Few of them adhere to the FAIR principles.
  3. Those that do, notably FAIR4RS (the FAIR principles for Research Software), are broad in scope and aimed at software developers, which may be part of why researchers have not widely adopted them.

Underlying all three is a distinction between analytical code and software.

Software is written to be general, modular and tested, and to work across systems with many different compatible datasets. Designing for that kind of reuse is genuinely complicated.

Analytical code is tailored to one dataset and one study. Its purpose is to be a transparent, reproducible record of that analysis, not to become a tool for other people.

Holding analytical code to software standards therefore sets an unrealistic target, and researchers faced with an unrealistic target tend to give up on it entirely. TADA instead sets a minimum standard that is achievable at any level of coding experience while still delivering the transparency and computational reproducibility that sharing is meant to provide.

2.2 The scale of the problem

The numbers, all from the TADA paper’s review of the literature, are stark:

What Figure Primary source
Journals in ecology & evolutionary biology with code-sharing policies 15% in 2015, rising to 88% in 2024 Mislan et al. 2016; Culina et al. 2020; Ivimey-Cook et al. 2025
Articles in the field with open code 5–35%, depending on the study various
Archived R files in Harvard Dataverse failing to run without error 74%, falling to 56% after automated cleaning Trisovic et al. 2022
Scripts in species distribution and abundance papers that did not run, or ran with errors 93% Kellner et al. 2025
Meta-analyses computationally reproducible given working data and code between 27% (every result matching exactly) and 73% (half of results within 10%) Kambouris et al. 2024

Journal policy has changed a great deal over the past decade; practice has been much slower to follow. Even where code is present and does run, computational reproducibility still cannot be assumed.

2.3 The four principles

Each has its own chapter. This is the one-paragraph version of each.

T Transferable Anyone can open the file, view it and run it without conversion or alteration, on a different computer and a different operating system. Standard file extensions, and no local file paths.

A Available The code is publicly archived so that any external user has long-term access to it, with a globally unique persistent identifier such as a DOI that is cited in the manuscript.

D Documented Accurate, detailed metadata, typically a README, describing the code files and their usage: environment, versions, licence, where the data are, and what runs in what order.

A Annotated Comments inside the code, or code embedded in RMarkdown or Quarto alongside descriptive text, explaining what each chunk does, why it is needed and where its output appears in the paper.

2.4 What TADA does not cover

The TADA paper is explicit that three things sit beyond its scope, while noting that all three support reproducible analyses:

  • Dependency and environment managers (renv in R, {conda} in Python), which help ensure the same computational environment is used each time, for example via a lockfile.
  • Containerisation (Docker, Apptainer — formerly Singularity), which packages a complete software environment of programs and libraries into an image so that the environment itself is reproducible between systems. This is the standard answer to the “works on my computer” problem.
  • Workflow managers (Snakemake, Nextflow), which specify the sequence of scripts or computational steps in a pipeline and their dependencies, so that each step executes in a defined, reproducible order.

None of these is a requirement of TADA. All three are worth knowing about; see Further reading.

2.5 How TADA maps onto FAIR

TADA was built with the FAIR and FAIR4RS principles in mind. Each letter maps onto one or more of them, and in two cases deliberately goes further.

FAIR principle Definition Covered by
Findable Digital assets (metadata, data, code) can be easily found by both machines and humans Available, through the provision of a unique identifier, and Documented, through the provision of rich metadata
Accessible Assets are retrievable via their identifier, with or without authorisation or authentication Available, since the code is retrievable via that identifier
Interoperable Assets can interoperate with other assets, and are readable using standard documented formats Transferable, extended to also mean runnable on different computers and operating systems
Reusable Assets are described sufficiently to enable reuse and attribution, ideally via a licence Documented, through a README and a licence, and Annotated, through commenting within the code itself

All four rows are stated in the TADA paper, not inferred by the wiki. In the paper’s own words: Transferable “corresponds to the FAIR principle of interoperability… and extends it”; Available “corresponds to the FAIR principles of both Findable… and Accessible”; Documented “corresponds to… the FAIR principle of Reusable… and Findable (the provision of rich metadata)”; and Annotated, “similar to documentation, corresponds to the FAIR principle of Reusable… but rather than describing the code ‘externally’, provides clear commenting within each coding script.” Documented and Annotated therefore share the same FAIR principle (Reusable), distinguished only by whether the description sits outside the code (a README) or inside it (comments).

Transferable is broader than Interoperable. Interoperability means anyone can open and use your code. Transferability adds the requirement that it also runs on someone else’s machine and operating system, which is precisely where hard-coded file paths cause problems.

Annotated shares its FAIR principle with Documented, not with a principle of its own. Both map to Reusable, since both are ultimately about enabling someone to understand and reuse the code; they differ in where that description lives, externally in a README (Documented) or internally as comments (Annotated). Annotated remains the letter most specific to research code, in the sense that FAIR is largely concerned with machines finding and parsing assets, whereas annotation is about a human being able to follow what the analysis actually did — and it is the letter most often skipped.

On “reusable”: the word is used in two different senses. In the FAIR sense it means sharing code in a way that clearly specifies what can be done with it, through a licence and a README. In the software-development sense it means writing generalised, modular, tested code that runs across systems and datasets. TADA targets the first. If you meet a guideline demanding the second, check whether it was written for software.

2.6 Languages

TADA is tailored mainly to R and Python, because those are the open-source languages most widely used in ecology and evolutionary biology. The basic principles apply just as well to workflow languages such as Snakemake and compiled languages such as C++ and, as the authors note, to disciplines other than ecology and evolutionary biology.

Where a language does not save code in a standard file type, apply the Transferable test: can the resulting file be opened by a plain text editor? SPSS syntax .sps files, for instance, pass.
