1 Start here

This chapter is for the situation most people are actually in: a paper is going out, and the code behind it sits in a folder whose logic made sense at the time. What follows is the shortest route from that to something a stranger can download, open and run.

Make four passes over the project, roughly in this order. Fix the paths and file types, archive it and get a DOI, write the README, then annotate the scripts. Finally, ask a colleague to run the whole thing before a reviewer has to.

The most useful check on this page is to download your own archived deposit into a fresh, empty folder, ideally on a different machine, and run it. Wiki guidance: this is the cheapest way to catch the failures the SORTEE guidelines group under Stage 5, meaning paths, missing packages and missing files. It will not catch the Stage 6 failures, such as stochasticity and version sensitivity, which need a seed and a documented environment instead.

1.2 A project layout that works

The example tree below is wiki guidance; the two conventions it embodies are from Ivimey-Cook et al. (2023, §3.1). The specific layout matters less than the result: a reader can see the order and purpose of every file without asking you.

my-project/
├── README.md                 <- start here: what this is, how to run it
├── LICENSE                   <- how others may use the code
├── my-project.Rproj          <- or a Python virtual environment
├── data/
│   ├── raw/                  <- never edited by any script
│   │   └── caterpillars_2024.csv
│   └── processed/            <- written by 01_, read by 02_
│       └── caterpillars_clean.csv
├── R/                        <- or scripts/, or src/
│   ├── 01_clean_data.R
│   ├── 02_fit_models.R
│   └── 03_make_figures.R
├── functions/                <- helpers sourced by the scripts above
│   └── utils.R
└── output/
    ├── figures/
    └── models/               <- saved model objects for slow fits

Most of the work is being done by two conventions.

  1. Numbered scripts. A reader knows the order to run things in without being told: 01_, 02_, 03_.
  2. data/raw/ is read-only. Cleaning writes to data/processed/. Raw data are never modified or overwritten by a script, so a botched cleaning step cannot destroy the original.

1.3 Three common causes of failure

Mistake Why it breaks Fix
setwd("C:/Users/ed/Desktop/analysis") The path exists on exactly one computer Open the project through its .Rproj file, or start Python inside the project folder, and build paths with here() / pyprojroot
Code shared as a .pdf or .docx Copy-pasting silently mangles apostrophes, quotes and whitespace, and drags in line numbers and headers Save as .R / .py
No set.seed() before a simulation or MCMC run Results change every run, so nobody can tell a real mismatch from noise Set a seed at the top of each independently runnable section

The .pdf and .docx problem is worse than it appears. The characters that get substituted, such as curly apostrophes for straight ones and non-breaking spaces for ordinary ones, produce errors that are hard to see and slow to fix, because the code still looks right.

1.5 What happens next

If your target journal has a data editor, someone will check your deposit against something close to the SORTEE guidelines: six stages running from whether the code is archived under a licence through to whether the results actually come out the same. Reading that section tells you what those checks are before anyone applies them to your submission.

If your journal has no data editor, the checks still matter. They simply fall to you and your co-authors instead, which is what code review provides.
