6 A — Annotated

Annotation is adding comments within each code file, denoted with # in R and Python, or embedding code within an RMarkdown or Quarto document alongside descriptive text. It improves both a reader’s ability to understand your archived code (transparency) and their ability to run it (functionality and reproducibility).

Annotation is the letter with no direct FAIR equivalent, and the one most often skipped. It is also much less work done while writing than reconstructed afterwards.

6.1 Annotate chunks, not lines

The recommendation is explicit: annotate code chunks rather than every line of code. Line-by-line annotation is possible, but denoting and describing the relevant chunks in sufficient detail is usually more helpful for tracking what the code does and what it produces.

A good chunk comment answers three questions:

  1. What is this chunk doing? “Run a Poisson generalised linear model…”
  2. Why is it needed? “…to analyse caterpillar abundance varying with habitat…”
  3. Where does its output appear? “Numeric results shown in Caterpillar Abundance section”, or “Figure 5A”

The third question is signposting, and it is the part people leave out. It is what lets a reader, a data editor or a reviewer connect a number in your results section to the lines of code that produced it.

Before

m1 <- glm(n ~ habitat + year, family = poisson, data = dat)
summary(m1)
plot(dat$habitat, dat$n)

Nothing tells a reader what is being run, why it is being run, or what it produces. There is no signposting at all.

After

##### Caterpillar abundance model #####
# Poisson GLM of caterpillar counts against habitat type, controlling
# for year, to test H1 (abundance differs between woodland types).
# Produces the coefficients reported in Table 2 and the numbers quoted
# in Results, "Caterpillar abundance".
m1 <- glm(n ~ habitat + year, family = poisson, data = dat)
summary(m1)

##### Figure 3A #####
# Raw counts by habitat, plotted as the left panel of Figure 3.
plot(dat$habitat, dat$n)

6.2 Collapsible sections

Certain comment markers create collapsible sections in the editor, which increases readability and helps structure a file. This is most useful in long scripts.

  • ##### in RStudio
  • #%% in Python
##### 1. Load and clean data #####
# ...

##### 2. Fit models #####
# ...

##### 3. Figures #####
# ...

In RStudio these appear in the document outline, so a reader can navigate a 600-line script from a sidebar instead of scrolling.

6.3 Literate alternatives

Rather than commenting a plain script, you can embed the code within a document alongside descriptive text. The TADA guidelines list this as an equally valid route to being annotated.

RMarkdown / Quarto

Prose and code chunks sit in one file, with the output rendered inline. The narrative is the annotation, and the link between a paragraph of explanation and the code that follows it is unambiguous.

## Caterpillar abundance

We fitted a Poisson GLM of counts against habitat type, controlling for
year, to test whether abundance differs between woodland types. These
coefficients are reported in Table 2.

```{r abundance-model}
m1 <- glm(n ~ habitat + year, family = poisson, data = dat)
summary(m1)
```

The SORTEE guidelines highlight a further advantage: presenting everything in one self-contained Markdown or Quarto document is very helpful for data editors and future readers, because it makes the link between the code, the data and the resulting outputs explicit.

A rendered .html or .pdf of your Quarto document is a useful addition to the archive, but archive the .qmd or .Rmd source as well. A rendered PDF on its own fails Transferable.

Jupyter Notebook

Notebooks, and JupyterLab, present code in chunks with descriptive text and inline output, and are listed in TADA as an alternative route to annotated code.

Two cautions when archiving a notebook (wiki guidance):

  • Restart and run all before you archive. A notebook whose cells were run out of order records a state that nobody can reproduce.
  • Notebooks store output in the file. That is useful for readers, but it means the archived .ipynb can be large and awkward to diff. Consider archiving both the notebook and a plain .py export.

Plain scripts

A well-commented .R or .py file is perfectly adequate, and for many analyses it is the clearest option. The requirements are the same:

  • logical chunks, marked with ##### or #%%
  • a comment on each chunk giving what it does, why it is needed and where the output appears
  • object names that a reader can follow

If the analysis is long, split it across numbered scripts (01_, 02_, 03_) and describe the order in the README.

6.4 Readability

Annotation works best on code that is already legible. The code review paper identifies four practices that make code reviewable, and they are set out in Writing reviewable code: calling packages explicitly by namespace, using relative file paths, removing redundant packages, and writing code with clear subheadings, intuitive comments and interpretable object names.

Tooling can enforce a consistent style. styler (Müller & Walthert 2020) reformats R code to a standard style in one command, and pycodestyle (Rocholl 2022) checks Python code against PEP 8, with black or autopep8 to do the reformatting. Supported styles include Google and tidyverse in R, and PEP 8 in Python.

Style is not the same as annotation. A perfectly formatted script with no comments still fails the Annotated test. Comments and signposting matter more than layout.

6.5 Annotating as you go

The SORTEE guidelines make the point plainly. Annotating code as you produce it, not only with section descriptions but also with information about how the code runs and what output it produces, is far easier than going back and annotating at the end of the study. The same applies to the README: create it at the start and update it as files are added.

The gain is not only in effort saved. Annotation written months after the fact is reconstructed from memory, and is more likely to describe what you intended the code to do than what it actually does.
