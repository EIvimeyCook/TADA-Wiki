Welcome

Best practice for code sharing

Code that still runs when someone else opens it

Most of the analytical code behind published papers is never shared, and a good deal of what is shared does not run. This wiki covers four things you can do to a project before you submit it that, between them, fix most of the problem.

What this wiki is

Sharing code is essential for transparency and computational reproducibility, and journal policies increasingly require it. Even so, the proportion of papers in ecology and evolutionary biology that share code remains low, with reported rates ranging from roughly 5% to 33%, well behind the equivalent figures for open data. Code that is shared also frequently fails to run. In a review of over 9,000 R files archived in the Harvard Dataverse, 74% failed to complete without error, and that figure only fell to 56% after automated cleaning (removing local file paths and fixing library installation and loading). A study of species distribution and abundance papers abandoned its reproducibility assessment altogether because 93% of scripts either did not run or ran with errors.

One reason is that researchers are rarely taught how to archive analytical code. The resources that do exist are written largely for software developers, not for someone preparing a one-off analysis of a single dataset.

TADA (Transferable, Available, Documented, Annotated) is a set of simple guidelines aimed at that gap. This wiki expands them into a working reference and sets them alongside the practices that go with them: metadata, licences, repository choice, the SORTEE data and code quality control guidelines, and code review.

The four principles

T Transferable Anyone can open your file and run it on their own machine, without converting or editing it first.

A Available The code is publicly archived somewhere immutable, with a persistent identifier (a DOI) that is cited in the paper.

D Documented A README describes the files, the software environment, the licence, and where the data live.

A Annotated Comments inside the code say what each chunk does, why it is needed and which result in the paper it produces.

TADA is deliberately a minimum standard. Analytical code is usually written for one dataset and one study, and its job is to be a transparent, reproducible record of that analysis rather than reusable software. TADA sets the bar at what that job requires, and maps onto the FAIR principles as it does so.

Who this is for

Researchers at any level of coding experience who need to share the code behind a paper. The examples use R and Python, since those are the languages most used in ecology and evolutionary biology, but the principles apply equally to workflow languages such as Snakemake, to compiled languages such as C++, and to disciplines well beyond ecology.

You do not need to know Git, Docker or unit testing to follow this wiki. Where those tools are useful they are mentioned, but always as optional extras rather than requirements.
