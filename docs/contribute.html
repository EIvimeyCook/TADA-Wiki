10 Contribute

This wiki is intended to be added to. If you have a worked example, a repository comparison, a language-specific pitfall, or a correction, this page explains how to get it in.

Copy templates/page-template.Rmd, fill it in, add the filename to _bookdown.yml, run Rscript render.R, and open a pull request. The rest of this page is detail.

10.1 What belongs here

Yes, please:

  • Worked examples: a real README, a real project structure, a real code review
  • Language- or tool-specific guidance (Julia, MATLAB, Stata, Snakemake…)
  • Discipline-specific notes. TADA was developed in ecology and evolutionary biology, and the authors explicitly encourage adaptation to other fields
  • Repository, licence or journal-policy information that has changed
  • Corrections, especially anywhere this wiki has drifted from the source papers

Probably not:

  • General programming tutorials. Link to them from Further reading instead
  • Advocacy for a particular statistical method
  • Tool recommendations with no connection to sharing, archiving or review

10.2 Sourcing

Separate what the papers say from what you are adding.

If a claim comes from one of the three source papers, state that and cite it, by author and year, so that a reader can find it in References. If it is your own practical advice, label it wiki guidance, as this wiki does throughout.

This separation is what makes the wiki usable. A page that blends sourced findings with the contributor’s own advice leaves a reader unable to tell which is which.

Concretely:

The SORTEE guidelines require that code files are in an interoperable format (Guideline 3.4). ✅ sourced, and pinpointed

Wiki guidance: in practice, the quickest way to check this is to open every file in a plain text editor before you deposit. ✅ labelled as an addition

You must always use .csv for data. ❌ unsourced, and stronger than the source

10.4 Adding a chapter

  1. Copy the template.

    cp templates/page-template.Rmd 12-my-new-chapter.Rmd

  2. Give it a heading and an ID. Every chapter starts with a level-1 heading carrying an explicit ID, because other pages link to it:

    # My new chapter {#my-new-chapter}

  3. Register it in _bookdown.yml, in the position you want it to appear:

    rmd_files:
  - "index.Rmd"
  ...
  - "12-my-new-chapter.Rmd"
  - "11-references.Rmd"   # keep references last

  4. Build and check.

    Rscript render.R

    Open docs/index.html.

Nothing validates your links. A broken ](#some-id) cross-reference does not fail the build, or even warn: it renders as a dead link and the build still exits successfully. Check new links by hand in docs/, or grep the built site for the anchor you expect.

10.5 Writing conventions

Cross-references

Link by ID: [Transferable](#transferable), [the four Rs](#review-four-rs). Give every section you might want to link to an explicit {#id}, because auto-generated IDs change when you edit a heading and silently break links.

Callouts

Four are defined in assets/style.css. Use them sparingly, since callouts lose their effect if most of a page sits inside one.

::: {.tada-key}
The short version — one paragraph that summarises the section.
:::

::: {.tada-tip}
Try this — a concrete, actionable suggestion.
:::

::: {.tada-warn}
Watch out — a common, costly mistake.
:::

::: {.tada-note}
Note — a caveat, exception, or aside.
:::

Tabs

Wrap the panes in a .tabset div. Each heading inside becomes a tab label, so mark them {.unlisted .unnumbered} to keep them out of the contents listing and out of the section numbering.

::: {.tabset}

#### R {.unlisted .unnumbered}

...

#### Python {.unlisted .unnumbered}

...

:::

assets/tada.js finds any element with the tabset class, so putting {.tabset} on a heading instead (## How to do it {#some-id .tabset}) also works. Use the div form in chapters, because it makes the extent of the tab group explicit.

With JavaScript disabled every pane renders in sequence, so never put anything in a tab that the page depends on being hidden.

Before / after code

Use :::: for the outer fence. Pandoc nests same-width fences correctly either way, but the wider outer fence makes the grouping obvious to the next person editing the file.

:::: {.tada-compare}
::: {.tada-before}
Before

```r
setwd("C:/Users/me/project")
```
:::

::: {.tada-after}
After

```r
library(here)
```
:::
::::

Checklists

End substantial chapters with one. Markdown task syntax, one item per line:

- [ ] Something the reader can verify in under a minute

Keep every item in the same grammatical form: a declarative statement of the finished state, not a mixture of imperatives and noun phrases.

Code chunks

Chunks are set to eval = FALSE globally in index.Rmd, because code on this wiki is illustrative and is never executed at build time. If you genuinely need a chunk to run, set eval = TRUE on that chunk and state the dependency in your pull request, because it becomes a build requirement for everyone.

To show an R chunk as an example inside a fenced block, use knitr’s verbatim engine, as Annotated does. Without it, knitr finds the inner chunk header and executes it, and the header vanishes from the rendered page:


```` markdown
```{r example-chunk}
1 + 1
```

````

Voice

  • Second person, present tense. “Save your code as .R”, not “code should be saved”.
  • State the guideline, then give the reason for it. The reason is what makes it memorable.
  • Prefer concrete numbers to adjectives. “74% of archived R files failed to run” beats “many files fail to run”.
  • Assume the reader is a competent researcher who has never archived code before, rather than a novice programmer or a software engineer.
  • British spelling throughout (licence as the noun, license as the verb; organise, analyse). Direct quotations from the source papers keep their original spelling.

10.6 References

Add new sources to 11-references.Rmd, alphabetically by first author, in the existing format:

**Author, A. B., & Author, C. D.** (Year). *Title of the work.* Journal
Volume: pages. <https://doi.org/…>

Include a DOI wherever one exists. If you cite something in a chapter, it must appear in that list.

10.7 Submitting

To propose a change:

git checkout -b add-julia-guidance
git add 12-julia.Rmd _bookdown.yml 11-references.Rmd
git commit -m "Add Julia-specific transferability guidance"
git push -u origin add-julia-guidance

Then open a pull request describing what you added and where it came from, whether sourced from a paper or from your own practice.

For small corrections, the Edit this page link in the footer of every chapter is quicker: it opens the source .Rmd on GitHub, ready to edit.
