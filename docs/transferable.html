3 T — Transferable

Transferability is the ability for anyone to open the file, view and run the code without conversion or alteration. It covers the FAIR principle of interoperability, meaning that anyone can open and use your code, and extends it so that the code also runs on different computers and operating systems.

Transferability has two independent requirements, and satisfying one does not compensate for failing the other.

  1. The code is saved in a file type any text editor or IDE can open.
  2. The code contains no paths specific to your machine.

3.1 Save code in an interoperable file type

Save code with an extension that matches the language: .R, .py, .cpp, or the equivalent standard format. These can be viewed, edited and saved by any text editor or IDE (RStudio, VS Code, PyCharm) on any system.

Do not share code inside .PDF or .docx files. A PDF can be viewed, but it cannot be opened and edited in an IDE without extra libraries or software, or without first converting it to another file type.

The deeper problem with PDFs and Word documents is what happens when someone copies out of them. Copy-pasting from these formats can change characters, of which apostrophes are the classic example, alter white space, or drag in unwanted extras such as line numbers and headers. The resulting errors are sometimes difficult to spot or time consuming to fix, because the code looks correct.

A note on .txt. A plain text file does let people copy and paste without those problems, but it introduces a different one. Many IDEs infer the coding language from the extension, so without the .R extension an IDE may not recognise the file as R and may refuse to execute it until it is re-saved. Use the language’s own extension.

If your language does not use a standard file type, apply this test: can the resulting file be opened by a text editor? SPSS syntax .sps files, for example, can be read in a text editor, so they pass.

3.2 Avoid local and user-specific file paths

This is one of the most common reasons that code which ran perfectly well for its author fails for everyone else (SORTEE, Stage 5).

File paths must be written so that they do not depend on your local environment or directory structure, which means using relative file paths rather than local or user-specific ones. It also means putting data, code and all necessary materials in a single project directory, since a relative path has to be relative to something.

Before

setwd("C:/Users/ed/Desktop/caterpillar_paper/analysis")
dat <- read.csv("caterpillars_2024.csv")

This sets a working directory that exists on exactly one computer, running one operating system, belonging to one person. Everyone else gets an error before the data have even loaded.

After

library(here)
dat <- read.csv(here("data", "raw", "caterpillars_2024.csv"))

This is independent of the operating system and of where the project folder sits, so anyone who downloads the project can load the data.

How to do it

There are several options, and they combine.

R

Use an RStudio project. File → New Project creates a .Rproj file. Open the project and RStudio automatically sets the working directory to the project folder, so setwd() is never needed. See https://docs.posit.co/ide/user/ide/get-started/.

Use the here package (Müller & Bryan 2020). here() builds paths relative to the project directory, whatever the operating system:

library(here)

raw     <- read.csv(here("data", "raw", "caterpillars_2024.csv"))
clean   <- here("data", "processed", "caterpillars_clean.csv")
figure  <- here("output", "figures", "fig3_abundance.png")

Use both. The TADA authors recommend RStudio projects and here together to maximise transferability across operating systems.

Without an IDE, launching R from inside the project directory achieves a similar effect.

Whatever you do, avoid setwd(). It sets a path that is specific to both the operating system and the user, and it is a frequent cause of errors when other people run your code.

Python

Use pyprojroot (Chen 2023), the Python counterpart to here, which builds file paths relative to the project directory regardless of operating system:

from pyprojroot import here
import pandas as pd

raw = pd.read_csv(here("data/raw/caterpillars_2024.csv"))

Work inside the project directory. Running an instance of Python within the project folder removes the need for local file paths.

Avoid os.chdir(), the Python equivalent of setwd(). It has the same problem: it hard-codes a path that only exists on your machine.

Other IDEs

VS Code. Navigate to the project folder and open the folder rather than the individual file. This performs a similar action to using an RStudio project, in that the workspace root becomes the reference point for relative paths.

Standalone interpreters. Launching R or Python from within the project directory does the same thing. The working directory is the project, and every path in the code can be relative to it.

Any language. The principle does not depend on the tool. Organise everything into one project directory, then write every path relative to the top of that directory.

Whichever method you choose, state it in the code documentation. Someone opening your project needs to know that they are expected to open the .Rproj file, or activate a virtual environment, before running anything. See Documented.

3.3 Beyond TADA: environments and pipelines

All of the following sit explicitly beyond the scope of TADA, but they are worth knowing about, because they address failures that relative paths alone cannot fix.

Dependency and environment managers, such as renv (Ushey 2023) in R and {conda} in Python, help ensure the same computational environment is used each time a project is run, typically via a lockfile.

Containerisation, through Docker (Merkel 2014) and Apptainer, formerly called Singularity (Kurtzer et al. 2017), uses images that encapsulate a complete software environment, including all required programs and libraries. This helps ensure environment reproducibility between systems and avoids the common “works on my computer” problem.

Workflow managers, such as Snakemake (Köster & Rahmann 2012) and Nextflow (Di Tommaso et al. 2017), specify the sequence of scripts or computational steps in a pipeline and their dependencies, ensuring that each step executes in a defined and reproducible order.

None of these is required by TADA. If you are already comfortable with them they strengthen transferability considerably, but relative paths and a good README will get you most of the way on their own.
